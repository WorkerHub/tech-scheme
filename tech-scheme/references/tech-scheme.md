## 1. 一句话方案

**Cloudflare 单栈 + 共享 D1 + 应用内鉴权 + GitHub Actions 自动部署。**
新项目只写自己的业务，基础设施（账号、库、密钥、前缀、登录、部署关口）全部复用组织级标准，不再逐项目发明。

适用画像分三档，基础设施相同、账号模型不同：

| 档位 | 代表项目 | 账号模型 |
|---|---|---|
| 单人版 | 个人站点类 | setup 只建唯一所有者，不开放注册，无角色分级 |
| 小圈子多用户版 | 多用户内容/通知类 | 开放注册但默认待管理员批准；admin / user 两级；数据按 `user_id` 接口层隔离 |
| 工具版 | 数据与工具类 | 沿用同一鉴权；业务对象各自建模，不套前两档的业务表 |

## 2. 总体架构

```
访客 / 登录用户
  → Cloudflare DNS（*.oneboy.app）
  → Worker（Hono）+ Workers Static Assets（前端同部署单元）
      ├─ 公开接口：只查公开数据，可缓存
      ├─ 私有接口：Cookie 会话校验，未登录 401 JSON + no-store
      ├─ Cron Triggers（如需定时：提醒、投递、清理）
      └─ 外部扇出（如需：SMTP / Telegram / 企业微信 / Webhook 等）
  → D1（组织共享的唯一一个库，按 TABLE_PREFIX 隔离）
  → KV / Durable Objects / R2：按需才开，不是默认件
         （KV 做 dedupe/缓存；DO 做强一致注册表；R2 做背景图/图标上传）
GitHub（WorkerHub 组织）— 合并 main → GitHub Actions → wrangler deploy → Cloudflare
Multica（Oneboy 工作区）— Muse 写规格/派单，Mike 拆单调度，Daniel/Mary 实现，Tony 评审，Jim 验证；合并/部署关口归用户
```

## 3. 技术栈（已定标准，不再逐项目选型）

| 层 | 选型 | 说明 |
|---|---|---|
| 运行时 | Cloudflare Workers | 免费层约束是设计前提，不是事后优化项 |
| 后端 | Hono + TypeScript | 路由、鉴权、调度、扇出都在 Worker 内 |
| 前端 | React + Vite + TypeScript，pnpm monorepo（`web/` + `worker/`） | 与现行各项目一致 |
| UI | shadcn/ui Nova 为主；仪表盘向可用 Kumo（`@cloudflare/kumo`）；无样式/无障碍底座 Radix UI；可选风格库 Looseleaf（§3D，立项定版才启用） | 三者是同一标准栈的不同用途，不是三选一乱搭 |
| 图标 / 动画 / 布局 / 拖拽 / 状态 | Lucide / Motion / react-resizable-panels / dnd-kit / Zustand | 已有依赖能表达的，一律用依赖原生实现 |
| 富文本（确有需要时） | TipTap 受限版（post 定版：段落/标题/加粗/斜体/引用/列表/链接/分割线） | 邮件/公开渲染场景必须配 HTML 白名单消毒 |
| 存储 | D1 为默认且首选 | 不用 KV 代替关系数据；D1 强一致可避免 KV 式延迟与 dedupe 补丁 |
| 邮件（确有需要时） | SMTP 与 Resend 双通道（§7），部署时二选一 | SMTP 走 `cloudflare:sockets` 原生实现：465 隐式 TLS、其余 STARTTLS、不支持 STARTTLS 且有凭证时拒绝明文、AUTH LOGIN；Resend 走其 HTTP API |

**立规（每份规格和评审清单必带）：** 严禁在已有依赖可以正确表达的情况下自行设计实现组件和行为。

## 3A. 前端设计质量标准：获奖级 + 自审循环

本节是给实现者的前端设计质量标准，拆开就是三件事：

1. **目标（OBJECTIVE）：** 页面要做到「获奖级」视觉标准，对标 Awwwards / Webby Awards / FWA 的获奖作品（`BENCHMARK`）——是拿它们当审美标尺，不是抄它们的版式或内容；
2. **八个检查维度（CHECK），每个都要达到获奖级：**

   | 维度 | 通俗说 | 评审时看什么 |
   |---|---|---|
   | typography | 排版 | 字体搭配、字号层级、行高、字重对比是否成体系 |
   | whitespace | 留白 | 间距节奏、呼吸感，不是把页面塞满也不是空无一物 |
   | visual_hierarchy | 视觉层级 | 第一眼看哪、第二眼看哪，是否不用思考就成立 |
   | color | 色彩 | 配色是否克制且有识别度、对比度达标、暗色/状态色成套 |
   | motion | 动效 | 动效是否顺滑、有目的（引导/反馈），而非装饰性乱动 |
   | micro_interaction | 微交互 | hover、点击、加载、成功/失败等小反馈是否完整细腻 |
   | responsive | 响应式 | 手机/平板/桌面各断点都是设计过的，不是缩放凑合 |
   | originality | 原创性 | 有没有本项目自己的记忆点，而不是模板默认脸 |

3. **自审循环（LOOP）：** 页面做完后触发——逐项拿成品对照八维清单、与标尺比差距，发现差距就改（PATCH），改完回到循环再审一遍，直到一轮审下来找不到明显差距才结束（Ω）。

**落地口径（把「找不到任何可改进」翻译成可交付的标准）：**

- **终止标准（防无止境打磨）：** 至少完成一整轮自审 + 针对发现的差距全部修补 + 复审一轮；一轮复审无明显差距即过。最多循环 **3 轮**，第 3 轮仍有大的取舍分歧（如原创性 vs 可用性），把截图和分歧点提到合并关口由用户拍板，不许无限打磨拖住上线。
- 本节的优先范围只限**前端设计决策**（视觉呈现层），不推翻本方案其他条款：技术栈 (§3)、基础设施 (§4)、安全与隔离 (§5–§7) 冲突时以后者为准；无障碍、性能、可用性是底线，不为「获奖感」牺牲。
- 分级适用，避免工具页硬凹造型：
  - **门面页全量执行：** 各项目的首页与公开页、任何落地页——八维全查，自审循环全跑；
  - **工具/后台页同标尺、不同权重：** 同样过八维，但排序是可用性与信息密度 > 一致性 > 审美表现，不为展示效果牺牲操作效率（各项目的管理界面属此档）。
- 与既有设计工具的关系：ui-ux-pro-max 负责**动手前**产出设计系统（`design-system/<项目>/MASTER.md`），frontend-design 负责实现时的审美判断，本节负责**交付前**的质量线与自审循环；三者不冲突，工具不换、标准栈不换。
- 交付证据：前端子单/PR 须附一张自审表——逐维写「对标点 / 发现的差距 / 已做的修补 / 复审结果」，并附桌面 + 移动端截图。没有自审表，评审不放行。

## 3B. 主题切换：亮 / 暗 / 自动三档

- 每个项目都必须支持**手动切换主题**，共三档：**亮（light）/ 暗（dark）/ 自动（auto）**，交互形态参考 §3C 参考实现的主题切换控件；
- **自动** = 跟随操作系统 `prefers-color-scheme`，且系统主题变化时页面**实时跟随**、不需要刷新；
- 默认值为**自动**；用户的手动选择要持久化（未登录时存浏览器本地，登录后同步进用户个人偏好，见 §5A.3「设置」），下次打开直接生效；
- 防闪烁：主题必须在首屏绘制前就确定并应用（读已存偏好、用 `dark` class + CSS 变量切换整套 token，沿 §3 的 shadcn/ui 变量体系），不许先亮一下再变暗，也不许逐组件写两套样式；
- 适用范围是全站，含登录页、初始化页、「关于」页（未登录可见页面同样要跟随用户已选主题）。
- 实现参考：对照 shadcn-admin 的 ThemeProvider（见 §3C）——`light | dark | system` 三档、默认 system、监听系统变化实时切换，与本节口径一致。

## 3C. 后台参考实现：shadcn-admin

- 出处：`satnaing/shadcn-admin`。定位是 **§3A 分级里的工具/后台档的布局与组件参考来源**，不是项目底座：作者自己亦声明它不是 starter template，数据全为 mock。
- **只借鉴三件套**（借结构与组件，不整仓 fork）：
  1. **侧边栏后台骨架**：Sidebar + 顶栏 + 内容区的管理面布局（含折叠与移动端形态）；
  2. **设置页分区形态**：其 settings 分页组织方式可作 §5A.3 三页分区落地的排版参考（内容边界仍以 §5A.3/§5A.4 为准，不照搬它的字段）；
  3. **主题 Provider**：三档主题的现成实现路子（见 §3B）。
  全局搜索命令面板（cmdk）可作可选参考，是否上由各项目规格定。
- **明确不带入**：① Clerk 鉴权——与 §5 应用内自建鉴权冲突，相关代码一律不用；② mock 数据与 faker；③ 它的示例业务页（chats/apps 等）只看结构、用到的才借；④ 它的 OTP 分格输入页——与 §5B「单框 + one-time-code」冲突，借鉴登录页时验证码框必须按 §5B 改。
- **风格对齐警告**：它的 shadcn 风格是 new-york（slate），咱们的标准是 Nova——借组件时把样式迁到 Nova 的 token/CSS 变量上，**不许整包搬它的全局样式**，否则同项目起两套皮肤；它另有十余个组件为 RTL 做过定制（scroll-area、sonner、separator 及一批 RTL 改件），复制这些组件时留意：用 shadcn CLI 更新可能覆盖其改动，咱们无 RTL 需求，取舍在子单里写明。
- 路由与数据层（它的 TanStack Router / React Query）**不在参考范围**：本条不构成采用决定，存量项目维持各自现状，新项目如需引入另行拍板。

## 3D. 可选风格库：Looseleaf

- 出处：`kevintngo/looseleaf`（MIT，含其字体；2026-11-19 核查）。定位是 **shadcn/ui 的手绘风格变体**：纸面质感 + 手绘描边，组件、blocks 与装饰素材（手绘图标、贴纸、印章）成套。它是**可选风格库，不是默认皮肤**——默认仍为 Nova（§3）；是否选用在项目立项规格里定版，未定版不启用，存量项目不追改。
- **兼容性**：基于 React + Tailwind v4 + Radix，与标准栈同路；保留 shadcn/ui 全部组件的接口（props 与 `data-slot`），换风格不动 JSX 结构。接入走 shadcn registry（`@looseleaf`），组件以源码形式落地仓库、落地后即本项目代码，不是运行时依赖。
- **全项目统一**：选用即整站一套皮肤，不许与 Nova 在同一项目混搭（同 §3C 的风格对齐警告）；其手绘图标与素材只在选用项目内成套使用，未选用项目的图标仍用 Lucide。
- **字体边界**：自带字体 Kevin Sans 只覆盖西文、中文无字形——选用项目的规格必须先写明中文字体的回退方案，并确认中西文混排效果可接受，不许上线后才发现不成套。
- **其余标准不豁免**：§3B 三档主题（亮 / 暗 / 自动、防闪烁）与 §3A 设计自审在选用项目照常适用；它自述的无障碍达标（对比度、可见焦点、reduced motion 等）不作验收依据，仍按 §3A 实测。其样式 token 以 `--ll-*` 前缀自成一套并映射到 shadcn 语义变量，接入时以它的映射为准，不另起变量名。

## 4. 基础设施铁律（新项目规格/派单必带，缺一条不算合格规格）

### 4.0 仓库：必须是公共仓库

- 项目仓库建在 WorkerHub 组织下，且**必须是 public 公共仓库**（与 §5A.3「关于」页要给出开源地址相呼应，任何人可直达仓库）；
- 推论（与 §7 互为表里）：既然仓库全公开，密钥/凭证更**绝无可能**进仓库的任何文件与提交历史——公开仓库的泄漏是永久的，连「先提交、后删除」都不行；示例文件只许列键名（`.dev.vars.example` 等），真实值只走 GitHub Secrets → `$RUNNER_TEMP/secrets.json` 一条路。

### 4.1 组织级共享配置，只引用、不新建

- Organization secrets：`CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` / `D1_DATABASE_ID`
- Organization variable：`D1_DATABASE_NAME`（非敏感、保持明文）
- 仓库级 secret：`KV_NAMESPACE_ID`（各仓不同、逐仓建；不得建组织级同名项）
- 禁止建仓库级同名项（KV 除外，上一条），禁止把这些值硬编码进代码或 wrangler 配置。

### 4.2 共享 D1，只用一个库

- Cloudflare 免费层只有 10 个 D1 库额度，组织共用用户已建的**单一** D1 库，新项目不新建库。
- 迁移与 setup 只能创建/修改本项目生效前缀下的表，绝不动其他项目的表。
- 同库现状：多个项目已在同一库内共存，各项目生效前缀均为已显式配置值，大小写按原值保留；已下线项目遗留的表不得擅动。
- **风险注记：** 共享库 = 共享配额与共享爆炸半径：曾发生批量写吃光账号级 D1 写配额、连累同库其他项目的事故。批量写项目不得与生产服务同节奏猛写，禁止擅自 backfill；动手改存量库前，备份是前置关口。

### 4.3 表前缀：方案 1 三态（变量名统一 `TABLE_PREFIX`）

| 配置 | 生效前缀 |
|---|---|
| 未配置 | 项目默认前缀（各项目代码内常量，形如 `<project>_`） |
| 配置为自定义值 | 该值（按项目现有规范化：补尾 `_`、校验非法字符，不放宽） |
| 显式置空 | 无前缀（部署者自担撞表风险） |

配套规则，缺一不可：

1. 解析只发生在一处 helper（如 `tables()` / `getTablePrefix()` / `tbl()`），全仓表名一律经 helper，除默认常量外不写死最终表名；
2. 生效前缀在初始化（setup/首次迁移）**之前**确定，初始化后不可改；
3. setup 完成必须输出实际生效前缀，后台/系统信息可查；
4. CI 侧三态打通：GitHub `vars.TABLE_PREFIX` 未设与空不可区分，约定未设/为空 → 注入默认前缀，保留字 `none` → 注入空字符串，其他值原样注入，须写进 README；
5. **防存量静默切换（最高优先级）：** 存量项目升级时，先盘点生产实际生效前缀，合并前复核升级后解析结果与之**一致才可合并**；setup/迁移须识别「库中已存在另一前缀下已初始化的 schema」并中止报错，不得按新前缀自动初始化出一套空表（表象是数据全丢）。

### 4.4 迁移命名与账本

- **命名一律顺序编号：** 迁移名只用 `schema_vN`，N 为该项目内的迁移序号；基线恒为 `schema_v1`，新增迁移递增编号。不再用功能名式命名（如 `files_uploads_v1`）。
- **存量已应用名不改：** 已记入账本的迁移名一律保留原名——改名会让 runner 以为没跑过、部署时重跑。命名口径只约束新增迁移。
- **存量功能名增量的坍缩（可选、须双条件）：** 基线 DDL 已是最终形态、且全部存量库都已应用该增量，两条都满足才可把增量定义并入基线、回到单一 `schema_v1`，后续从 `schema_v2` 续号；账本里的旧名记录保留不管，不做生产库操作。
- **账本：** 已应用迁移记在 `_<生效前缀>schema_migrations`（前导下划线在前缀之前，标记内部表）；迁移只动本项目生效前缀下的表（§4.2、§4.3）。

## 5. 鉴权方案（移植现行标准实现，不新发明）

- **不用 Cloudflare Access**，登录在应用内完成，与公开页同一体验。
- 登录方式三件套：账号密码 + Passkey（WebAuthn）+ TOTP 二次验证；密码哈希、Passkey 凭证与 TOTP 密钥的存储/脱敏全部照现行标准实现。
- 会话：HttpOnly + Secure + SameSite Cookie；登录接口限流 + 连续失败锁定/延迟。
- 初始化：首次部署走 setup 流程——先凭 `SETUP_SECRET` 初始化数据库，再注册首个账号，该账号即管理员（单人版即唯一所有者）；流程细节与默认开关见 §5A。
- 注册口径按档位选（见 §1 表）：单人版不开放注册接口；小圈子版**默认开启注册、默认需要管理员批准**，批准后才能登录使用，管理员可批准/禁用；两个开关均可在「系统管理」里改（§5A.4）。
- 数据隔离在**接口层**做，不靠前端隐藏；多用户数据一律按 `user_id` 校验归属。

## 5A. 首次安装、页面分区与版本信息

### 5A.1 首次安装流程（setup）

1. 全新部署后数据库尚未初始化时，打开任意页面应**引导用户进入初始化页面**，而不是报错误或展示空应用；
2. 初始化页面只要求输入 **`SETUP_SECRET`**（部署侧 Secret，见 §7；页面与接口都不得回显它）。校验通过后执行初始化：按 §4.3 的生效前缀建表/跑迁移，完成后**明确输出实际生效前缀**；
3. 初始化完成后进入注册：**第一个注册成功的用户自动成为管理员**（且直接批准、不走待批准流程）；自第二个用户起按 §5A.4 的注册开关执行；
4. 首个管理员产生后，setup 的「建管理员」能力即关闭。已初始化的实例再次走 setup 只允许做幂等检查/迁移，**不得再创建管理员、不得覆盖已有数据**；探测到其他前缀下已初始化的 schema 时按 §4.3 第 5 条中止报错；
5. 存量衔接已闭环：post 此前是「`/api/setup` 凭 `SETUP_SECRET` 直接建首个管理员」的合一步骤，（先初始化数据库、后注册首个用户）。全组织口径统一，不再保留合一变体。

### 5A.2 未登录状态的版本号（页脚）

- 所有**未登录可见页面**（登录、注册、初始化、公开页）的**底部**必须显示当前版本号，格式为 git describe 风格：

  ```
  v1.3.0-8-479967d
  ```

  即 `v<语义版本>-<该版本标签之后的提交数>-<短 commit 哈希>`（`git describe` 原始输出带 `g` 前缀，如 `v1.3.0-8-g479967d`，展示时去掉 `g`）。无版本标签时用 `v0.0.0-<提交数>-<短哈希>` 兜底，不许不显示；
- 版本号与构建信息由 **CI 在构建时注入**（非密钥，可走构建变量/前端常量生成），**禁止在代码里写死**；与「关于」页（§5A.3）展示的版本号必须同源一致；
- 页脚只展示版本号本身即可，样式低调（小字、弱化色），不抢正文；登录后不作此要求（登录后看「关于」页）。

### 5A.3 三页分区：「设置」/「关于」/「系统管理」不许混

| 页面 | 定位 | 内容 | 可见性 |
|---|---|---|---|
| **设置** | 关于**当前用户本人**的 | 个人资料（昵称、邮箱）、安全（改密码、TOTP、Passkey 管理、会话/退出）、个人偏好（语言、时区，以及项目级个人选项（如默认渠道、时区）） | 登录即可见；只能改自己的 |
| **关于** | 关于**当前项目**的说明 | 项目名称与一句话说明、使用的技术栈（按 §3 列实际用到的）、开源地址（GitHub 仓库链接）、**当前版本号、构建日期、构建时间** | 登录页可达/登录后可见均可，内容不含任何敏感信息 |
| **系统管理** | 关于**全站**的配置 | 见 §5A.4 清单 | **仅管理员可见** |

- 三者的命名与边界是硬要求：不许把全站配置塞进「设置」，也不许把项目说明塞进「系统管理」；
- 「关于」页的构建日期/时间与 §5A.2 的版本号同为 CI 构建时注入（构建日期 `YYYY-MM-DD`、构建时间 `HH:mm:ss`，并注明时区），部署一次即固定，重部署才更新。

### 5A.4 「系统管理」内容清单与可见性

仅管理员可见，含五项：

1. **邮件发送配置**：通道二选一（SMTP / Resend）；SMTP 时配 host / port / username / password（脱敏返回、留空表示不改）/ from / from_name，Resend 时配 API Key / from；附「发送测试邮件」；
2. **是否开启注册**：开关，默认 **开**；
3. **注册是否需要审核**：开关，默认 **开**（需要管理员批准）；待批准用户的批准/拒绝入口也放在系统管理内（用户管理），否则审核开关无处执行；
4. **是否开启 setup 页面**：开关。初始化完成前 setup 页面必然开启（否则无人能完成 §5A.1）；初始化完成后默认关，管理员可在此重新开启——重新开启只露出入口，任何 setup 操作仍必须凭 `SETUP_SECRET`，且受 §5A.1 第 4 条约束；**开关只门控页面、不门控密钥接口本身**，端点与状态语义见 §5A.6；
5. **数据库状态（只读）**：展示当前生效前缀与账本已记录的迁移，供管理员核对。数据库升级由部署流程自动完成（§9 第 4 条），**管理面不提供升级按钮、不设管理面升级端点**；契约见 §5A.6 第 5 条。

可见性必须双层落地，照 §6 的原则：前端不渲染「系统管理」菜单只是表象，**接口层对非管理员一律 403**，普通用户直接拼 URL/调接口也拿不到、改不了。

### 5A.5 档位适配

- 多用户档：本节全量适用；
- 单人档：§5A.1 改为 setup 凭 `SETUP_SECRET` 初始化并创建唯一所有者（即管理员本人），不开放注册，第 2–3 项注册开关不适用、不展示；§5A.2 页脚版本号、§5A.3「设置/关于」分区、数据库状态只读展示照常适用，「系统管理」与所有者本人的设置可合并呈现，但命名边界仍按 §5A.3。

### 5A.6 setup 页面与数据库升级的接口契约

§5A.1 与 §5A.4 定的是「要有 setup 页面与开关」，本节把接口与语义落成契约，新项目与存量改造一律照此实现，不再逐项目发明细节：

1. **单内核、部署自动触发：** 迁移 runner 只有一个实现，只做前进式幂等迁移。触发入口收为一处：部署流程在部署后调第 4 条的密钥端点自动执行（§9 第 4 条）。setup 页面只负责初始化——未初始化时凭 `SETUP_SECRET` 建库并走完 §5A.1 的建所有者/引导注册；已初始化后页面只呈现状态，**不提供升级表单**；系统管理不提供升级入口（§5A.4 第 5 条）。
2. **状态端点：** 提供无需鉴权的 `GET /api/setup/state`（响应 `no-store`），返回页面可否访问与初始化状态（如 `{enabled, ownerExists, tablePrefix}`，字段名可按项目现行口径微调、语义不得变），不含任何密钥/哈希信息。setup 页面打开先查它再决定形态：未初始化 → 初始化形态；已初始化 → 只呈现初始化状态；页面已关闭 → 只显示「已关闭、去系统管理开启」提示，**已初始化态的 DOM 中不得出现密钥表单**。
3. **开关语义（只门控页面）：** 开关存项目设置表，键名 `setup_page_enabled`（`'1'` 开 / `'0'` 关）。**未初始化时页面恒开**，与存储值无关（防自锁）；初始化完成动作须**显式写入关闭值**作为默认，不得依赖「无此行」时的缺省解释（存量项目有缺省 `'1'` 的现状，新项目不得照抄此缺省）；管理员可随时重开。开关**只影响页面**，不影响第 4 条的密钥接口本身——密钥即门闩，关页面不等于停掉恢复路径。
4. **密钥端点（纯升级，与建账号分离）：** `POST /api/setup` 只跑迁移——不建用户、不改密码、不删任何数据；已初始化实例走它升级不再报「已完成」类错误。建首个管理员/所有者仍走 §5A.1 的既有流程端点（多用户档为初始化后注册，单人档为与初始化同页建所有者），两端点不得混为一个含糊实现。密钥规矩：只走请求头 `X-Setup-Secret` 做常量时间比较，**禁止出现在 URL/查询参数里**（不提供 GET 式 setup）；密钥未配/为占位符 → 500 失败关闭，不匹配 → 403；按来源 IP 限流（每 10 分钟 3 次，超限 429）。成功回显 `{success, tablePrefix, migrations: [{name, status}]}`（applied/skipped 逐条列明）；探测到其他前缀下已初始化的 schema → 409 并带可读 detail，密钥端点与管理面端点形状一致，且绝不建第二套表（§4.3 第 5 条）。部署自动升级步是它的标准调用方（§9 第 4 条）。
5. **管理面只读与开关：** 不设管理面升级端点（原 `POST /api/admin/setup` 撤除）；系统管理区可读当前生效前缀、账本已记录迁移与开关状态，开关写入走管理面专用端点并严格校验。可见性照 §5A.4 双层落地：未登录 401、非管理员（多用户档）403；单人档登录即所有者。
6. **防泄露：** `setup_page_enabled` 及 setup 相关内部状态不得进入公开数据出口——不进 `/api/public`、不进站点设置类公开 DTO、管理面读写只走专用端点，不借道通用设置白名单。
7. **setup 密钥框的填充信号（§5B 的延伸）：** setup 密钥不是登录密码：输入框 `id`/`name` 用强语义 `setup-secret`，`autocomplete="off"`，**禁用 `current-password`**，防密码管理器把登录密码误填进来；提交后立即清空输入。
8. **非目标：** setup 页面与系统管理**永远不提供破坏性操作**——删表、清库、重初始化只能是部署者在数据库控制台的手动动作，不许做成页面按钮（至多在规格/手册里给手动清单）。

## 5B. 登录表单与密码管理器自动填充规范

**原理：** 密码管理器综合 `type`、`autocomplete`、`name`/`id` 三个信号判断每个输入框的语义：TOTP 框若写成 `type="password"`、或 `name`/`id` 带 `password` 字样、或缺 `autocomplete`，会被当作密码框误填密码；正确标注 `autocomplete="one-time-code"` 时，管理器识别其为验证码框，并填入条目中保存的 TOTP 验证码。

**规范（登录/注册/改密所有表单一律照此写，进评审清单）：**

| 字段 | type | autocomplete | name/id |
|---|---|---|---|
| 用户名/邮箱 | `text` / `email` | `username` | `username` / `email` |
| 密码 | `password`（全流程**只有密码框**可用此 type） | 登录 `current-password`；注册/改密 `new-password` | `password` |
| TOTP 验证码 | `text`（**禁止用 `password`**） | **`one-time-code`** | `totp` / `code` 等，**不得含 `password` 字样** |

配套要求：

- TOTP 框加 `inputmode="numeric"`，用**单个输入框**，不用六个单字格（分格输入会让自动填充无所适从）；
- 密码步与 TOTP 步尽量**分步呈现**（先验密码、再进 TOTP 步的两步登录形态），同屏同时摆着密码框和验证码框最容易被管理器填串；
- 验收项：用 Bitwarden（vaultwarden）存好含 TOTP 的条目实测一遍——密码步只填账号密码、TOTP 步填入 6 位验证码而不是密码，才算过。

**补注：换步必须换节点**

属性全对仍可能误填：同页分步表单换步时，框架可能**原地复用同一个 input 节点**（属性全换、节点没换）；而密码管理器的页面采集**按 DOM 元素缓存、对已缓存元素不重读属性**，该节点在其眼里常驻第一步采集到的密码语义，填充时仍会把账户密码写进验证码框。此病灶只存在于换步过程，逐页静态渲染查不出来。

规范追加（与上表同级，进评审清单）：

- **换步 = 换节点**：凡步骤切换会改变输入框的语义角色（密码 → 验证码、登录 → 注册等），必须强制新建 DOM 节点——给两步的 `<form>` 或关键 input 加**不同的 `key`**，让框架卸载重挂；禁止靠原地改属性跨语义复用同一节点。这也是弹窗/跳页式二步天然免疫的原因（验证码框是新挂载的节点、首次采集即正确），同页换步必须用 key 人工达到同样效果。
- **防退化断言**：测试中断言换步前后的关键 input **不是同一元素**（如 `codeEl !== pwEl`），防日后重构把 key 弄丢、病灶复发。
- **验收方法**：涉密码管理器的复现与验收必须跑**真实框架渲染的完整换步流程**，最终以真机实测为准（同上验收项）。

## 6. 公开 / 私有隔离（共同定版的验收口径）

- `GET /api/public` 只返回公开数据，可边缘缓存；私有数据不打码、不占位、**完全不出现**。
- 私有接口必须带有效会话，未登录返回 **401 JSON**（供前端弹登录，不重定向到 HTML 登录页），响应 `Cache-Control: no-store`。
- 公开信墙/公开页同理：公开接口只查公开标记的数据（如 post 的 `is_public=1`），私有内容在未登录可达的接口、页面源码、缓存里零出现——列为评审必查项。

## 7. 配置与密钥分层

三层分工，不混放：

| 层 | 放什么 | 落点 |
|---|---|---|
| 组织级 | `CLOUDFLARE_API_TOKEN` 与共享库 ID/账号 ID | GitHub Organization secrets/variables |
| 仓库级 Variables | 本项目的普通配置（如 `TABLE_PREFIX`、`ALLOW_*` 开关） | GitHub repo Variables，CI 做占位符替换进 wrangler 配置 |
| 仓库级 Secrets | 本项目的应用密钥（`JWT_SECRET`、`SETUP_SECRET` 等，每项目值不同、隔离轮换）与资源 ID 中的 `KV_NAMESPACE_ID`（见红线 7） | GitHub repo Secrets → CI 生成 `$RUNNER_TEMP/secrets.json`（0600）→ `wrangler deploy --secrets-file` |

红线：

1. **失败关闭：** 生成 secrets.json 前逐键校验非空，缺任何一个立即中止部署并点名报错，绝不用空值覆盖 Cloudflare 现有 Secret；
2. **值不变原则：** 已上线项目首次 CI 化必须用与线上**相同的值**（用户本人填入 GitHub）；拿不出同值时，只对可轮换键逐键轮换（JWT 轮换 = 全员重登；SETUP 类影响可忽略；API Token 新建同权限后撤旧）；
3. **加密钥可进 CI、但永不许新值顶替：** `ENCRYPTION_KEY` / `TOTP_ENCRYPTION_KEY` 这类 AES-GCM 钥可以与其它键同路进 CI（GitHub Secrets + secrets-file 上传），前提是**值已妥善备份/存储**：密码管理器留底一份 + GitHub Secret 一份，只放在不可回读处等于没有备份（Cloudflare 控制台与 GitHub Secret 都是创建后不可回读）。铁律不变的是**值不变**：一旦换新值，库中密文（TOTP 凭据、保存的密钥配置）全部解不开；拿不出原值的存量钥事实上无值可填、保持 Cloudflare 现有 Secret 不动（`--secrets-file` 未包含的键不会被覆盖），要纳入只能连同轮换与存量密文处置单独拍板。新建项目的加密钥从生成第一天起就留底并进 CI；
4. secrets.json 只许落在 `$RUNNER_TEMP`，不得落仓库工作区靠 .gitignore 兜底；任何步骤不得打印/回显/上传含密钥的 artifact；
5. 资源 ID 不是密钥：放 Variables 还是 Secrets 不按是否敏感判断，按红线 7 的日志掩码定案执行；个别存量项目的不同放法属现状，不作新项目样板；
6. **语义例外要显式写进规格，不许套通用校验：** 「一次性播种源」（如用户注册表播种键，首次导入后以 DO 注册表为准）和「空 = 功能关闭」（如管理员密码哈希键）两类键不适用非空校验，改为有值才写入、为空整键省略。
7. **资源 ID 一律存 GitHub Secrets、不得以明文进公开日志：** 资源 ID 不是密钥，但 wrangler 的自身输出（`d1 execute` 横幅、`deploy` 的 Bindings 摘要）会把 `D1_DATABASE_ID`、`KV_NAMESPACE_ID`、`CLOUDFLARE_ACCOUNT_ID` 明文打进 GitHub Actions 日志，舰队仓库均为公开仓库、日志任何人可见。定案做法：三个 ID 改存 Secrets（组织级 `CLOUDFLARE_ACCOUNT_ID`/`D1_DATABASE_ID`、仓库级 `KV_NAMESPACE_ID`，见 §4.1），deploy 里经 `secrets.` 引用——Secrets 的值在 job 开始前即预注册为掩码，全部步骤（含第一个引用它的步骤）的 env 区与输出均自动打码。原 add-mask 方案有结构性残余（携带值的第一步 env 区在掩码注册前已被 runner 打进日志；属 GitHub runner 已知时序问题，actions/runner#475 五年未修），已实证并弃用，新仓库不得再用 add-mask 承担 ID 掩码。`D1_DATABASE_NAME` 不在此列（非敏感、保持 Variable 明文，掩了毁日志可读性）。历史日志不回溯。迁移规格另册存档。

**邮件发送通道：** 标准实现同时支持 SMTP 与 Resend 两种通道，部署时由用户二选一启用；两通道共用同一发送接口，切换不改业务代码。凭据（SMTP 密码 / Resend API Key）按仓库级 Secrets 存放，通道选择与非密参数放 Variables 或系统管理面（§5A.4）。

现状分派：各项目现状与 CI 化改造进度以各自项目单为准，本方案不维护项目状态。

## 8. 业务共性模式（按需取用，不强塞）

- **定时任务：** Wrangler Cron 触发（如每 5 分钟扫一次到期任务）；防重复优先用 **D1 状态抢占**——`UPDATE ... SET status='sending' WHERE id=? AND status='scheduled'`，影响行数为 1 才执行。存量项目已有的 KV dedupe 模式保留不强改，但注意其教训：解析/配置失败时**不写 dedupe 键**，修好配置后同一窗口还能补发。
- **定时任务接 waker 的双模式：** 唯一开关是 **`WAKER_SIGNING_KEY` 配没配**，不设任何模式变量——**严禁另设 `WAKER_MODE` 之类变量**，一个开关只认一处。未配 → 默认走 Cloudflare Cron Trigger，开箱即用、零 waker 依赖，waker 回调口 fail closed（回未配置响应、不执行）；配了（GitHub Secret → secrets-file 注入）→ waker 接管：waker 按计划发 HMAC 签名回调、项目侧验签后执行，原生 Cron 的处理函数检测到 key 存在即跳过让路（wrangler 的 triggers 配置保留）；删 key 并重新部署即自动回到 Cron。静态周期任务**只配 signing key 一把、不用项目令牌**（项目令牌仅项目需动态调用 waker 注册/管理 API 时才配，如需动态自续调度的项目）。模式互斥之外仍按上一条做 D1 状态/日志幂等兜底，防配置切换过渡期双跑。
- **发送/扇出类：** 解析逻辑只实现一处；「未选」的语义必须显式定义且**失败关闭**——定版口径为：选了按选的发（可多选），没选只发用户预设的**唯一默认渠道**，未设默认则报错不发，绝不退回「全量扇出」。新项目凡有「默认/兜底」语义，照此办理：无默认 = 报错，不许静默全量。
- **终态不变式校验：** 配置类写入按「落库后终态」校验而非单字段校验（如默认渠道必须在最终的已启用集合内，不满足整单不写），保证原子性。
- **迁移写法：** 命名按 §4.4（`schema_vN` 顺序编号）；schema 两处（`schema.sql` 与 setup 内嵌定义）必须逐字同步；存量加列走 `PRAGMA table_info` 查缺 + `ALTER TABLE` + try/catch 只记日志；清理/退役类迁移要连带清理关联字段，且幂等可重跑。

## 9. 部署与交付流程

1. GitHub Actions：合并 `main` 即自动部署——因此**合并就是部署关口，归用户拍板**，团队不自合、不自部署；
2. 合并前关口确认：同值 Secrets/Variables 已由用户配好（§7）、存量前缀复核一致（§4.3.5）、备份已完成（如涉及存量库）；
3. 仓库校验全绿才交付：typecheck / build / test（以各仓脚手架实际命令为准），外加三态解析、防静默切换等关键路径单测；
4. **部署后自动升级（deploy.yml 固定步，照模板定版实现）：** Deploy Worker 成功后，工作流调本项目的 `POST /api/setup` 执行迁移，不再由管理员人工触发：① 用 `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` 经 CF API 现查账号的 workers.dev 子域；② 查本 Worker 的 workers.dev 开关，未开则自动打开；③ `POST https://{worker 名}.{子域}.workers.dev/api/setup`，请求头 `X-Setup-Secret` 取 `secrets.SETUP_SECRET`，只经 env 传入、禁止回显；④ 网络错误 / 429 / 5xx 退避重试（约 5 次、总时长 ≤ 约 1 分钟），403 立即失败、不重试；⑤ 断言 HTTP 200 且响应 `migrations` 明细包含本次部署源码定义的全部迁移名（applied / skipped 均可、必须在场），明细打印进日志。任一不满足 → 本步失败、Deploy 变红。每次部署都执行、幂等（无待升级迁移时全 skipped 通过）。采用前提：`SETUP_SECRET` 为真值且与 Worker 侧一致——占位或不一致会失败关闭、Deploy 变红，先修 secret 再采用；本步不新增任何 secret / variable。交付说明仍须提醒上线即生效的行为变化（如默认渠道未设时提醒会断）；
5. 协作流程（与具体协作工具无关）：需求以父单承载、拆为子单执行，父子单挂同一项目；任务状态只用四态（未开始／进行中／审核中／完成）；调度角色只拆单调度、不写代码；跨项目引用一律写「项目名 #序号」。

### 9.1 手动发版：tag.yml + release.yml

每个项目仓库的 `.github/workflows/` 标配两个文件，与 ci.yml / deploy.yml 并列：

| 文件 | 触发 | 做什么 |
|---|---|---|
| `tag.yml`（Manual Release Tag） | **手动** `workflow_dispatch`，输入一个 tag（如 `v1.3.0`） | 校验格式 → 查 tag 不存在 → 在 `main` 上建 tag 并推送 |
| `release.yml`（Release） | push 了 `v*` 的 tag 后**自动** | 以该 tag 建 GitHub Release，`generate_release_notes: true` 自动生成发布说明；权限只需 `contents: write` |

定版细节，各项目照此执行、不得各自发挥：

1. **发版是纯手动动作**：合并 main 只管自动部署（持续上线），不自动打 tag；版本号是里程碑决策，由人决定何时发、发哪个号，在 Actions 页面手动运行 tag.yml 时输入；
2. **格式校验失败关闭**：tag 必须匹配 `^v\d+\.\d+\.\d+$`（语义版本），不合规直接报错退出；tag 已存在同样报错退出，不许覆盖、不许移动已发布 tag——版本号是公开承诺（仓库又是公共仓库，§4.0）；
3. **推送必须用 `PAT_TOKEN`，不能用默认 `GITHUB_TOKEN`**：这是整条链的关键机制——用默认 token 推的 tag 不会触发其他 workflow，release.yml 永远不会跑。`PAT_TOKEN` 是仓库级 Secret，由用户预先配好（按 §7 密钥规矩走 GitHub Secrets，团队不经手明文）；新项目建仓清单里要确认此 Secret 已就位；
4. tag 打在 `main` 的当前提交上，该提交本已部署上线——**打 tag 不触发重新部署**，发版与部署解耦；
5. 与 §5A.2 的版本号是一条链：页脚/「关于」的 `v1.3.0-8-479967d` 靠 git describe 数 tag，没有 tag 的项目版本号只会退化成 `v0.0.0-…` 兜底（已有项目踩过此坑）。养成手动发版习惯，版本号才有意义。

## 12. README 与截图规范

- **存放位置：** README 截图统一存仓库内 `.github/assets/imgs/`，README 用相对路径引用。理由：随仓库走，Fork/镜像/备份/离线 clone 都能显示，不依赖外部图床、不会死链；`.github/` 不进构建产物、不被 Wrangler 部署，不占 Worker 体积。组织门户做项目卡片时直接复用同一文件（raw/jsDelivr），不另存一份。
- **禁止：** 外部图床（Imgur、自建 R2 图床等）作主存；GitHub `user-attachments` 随机链接（不可整理/替换、迁出即丢，只许临时贴图）；把截图放 `public/`、`src/assets/` 等构建目录；未压缩原图直入仓库；Git LFS。
- **格式与体积：** WebP 为主（质量约 80，文字清晰度受损才用 PNG 并说明）；文件宽度 ≤1600px，桌面采集视口 1440×900、移动端 390×844，README 展示宽 800–900；单张 ≤300KB、单仓总计 ≤2MB。
- **命名：** kebab-case 语义名（`home.webp`、`dashboard.webp`、`settings.webp`、`mobile-home.webp`、`dark-home.webp`、核心功能页 `feature-<功能名>.webp`），不用日期或系统默认截屏名。
- **内容：** 每项目必备主界面、核心功能页、登录后工作区/管理页各一张；移动端与暗色模式图可选。README 在标题/简介后、功能与部署章节前设「界面预览」节，图片一律写有意义的 `alt`。
- **采集纪律：** 严禁用真实个人/生产数据入图，用演示/种子数据或测试账号；避不开的字段打码后才入库，评审逐张查。截图须为当前 main 对应版本的真实界面。
- **大体积演示：** GIF/录屏先转 MP4/WebM 控体积，仍超限的只放封面图进仓库、视频放该仓 GitHub Release 附件并链接。
- **更新：** UI 大改的 PR 须同步更新受影响截图；评审清单含路径/格式合规、体积合规、无敏感数据三项。
